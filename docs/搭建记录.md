# K12 官方信源看板 · 搭建记录

> 2026-10-22 搭建完成并上线。本文记录从需求到上线的完整过程：每一步的决策、踩的坑、以及为什么这么做，供后续维护和复用参考。
>
> 在线地址：https://xian492.github.io/k12-dashboard/ ｜ 仓库：xian492/k12-dashboard（私有）

## 一、需求起点

信源调研（学城《信源分析》总纲）确立了官方制度化信源是全部判断的锚点，但当时全部信源分析都是推理，缺一层「实际在看什么」的实证。已有的三套工具各有分工：MediaCrawler 管按需采集（小红书评论分析）、RSSHub + NetNewsWire 管订阅推送、但缺一个**打开就能看全盘的界面**——尤其给团队其他人看时，不能要求人人装 NetNewsWire。

由此确定看板定位：**20+ 路官方信源的最新条目、按区组织、自动更新、网页访问**。

## 二、架构决策

核心问题：RSSHub 跑在本地 Mac 上，无法部署成公网服务。三个备选：

| 方案 | 评估 |
|---|---|
| 把本机 RSSHub 暴露到公网（内网穿透/买服务器） | 要维护服务器，成本高 |
| 用公共 rsshub.app 实例 | 公司网络实测不可达（000），不可靠 |
| **GitHub Actions 定时构建静态页**（选定） | 零服务器、零依赖本地环境，代码公开可审计 |

选定方案的关键发现：**官方信源不需要 RSSHub 中转**。yjrx 的区政策是干净的 JSON 接口，市教委和教育部是可解析的静态 HTML——Actions 里直接拉原始接口即可，RSSHub 的角色只剩知乎 UGC（cookie 依赖），而知乎源按需求裁剪暂不上看板。这让看板成为一个完全独立的系统。

```
每 6 小时（北京 02/08/14/20 点）
GitHub Actions 跑 tools/build.py（纯标准库，零第三方依赖）
  ├─ yjrx 18 区 JSON 接口
  ├─ 市教委通知公告页（HTML 解析）
  ├─ 教育部公告页（HTML 解析）
  └─ 4 所学校官网（HTML 解析）
  → 生成 docs/index.html + data.json 快照
  → 部署 GitHub Pages + 数据快照提交回仓库（政策变化可回溯）
```

## 三、信源接入过程

### 3.1 yjrx 区级（18 路，最顺利）

调研区教委官网时发现：海淀、西城等区教委**没有独立官网**，区级招生政策的权威发布点是市义务教育入学服务平台（yjrx.bjedu.cn）的各区专区。进一步发现其政策列表是 JS 动态加载，但数据源是干净的 JSON：`/uploads/json/{fid}.json`，fid 从各区 `portal_{区缩写}/zszc.html` 页面源码的 `initPaginator()` 参数中取。18 个区全部验证 200。

这 18 路同时复用进了本地 RSSHub（自定义路由 `/yjrx/district/:fid`，见 `lib/routes/yjrx/`），一套发现两处受益。

### 3.2 市级（2 路，正则踩坑）

市教委页面 http→https 有 307 重定向，且通知链接格式是 `./202610/t20261021_4912964.html`（6 位年月 + 8 位日期），第一版正则 `\d{9}` 写错导致拉取为 0。修正为 `\d{6}/t\d{8}_\d+` 后拿到 20 条。教训：**写完正则必须先打印页面原始片段核对真实结构，不能凭记忆猜**。

### 3.3 校级（4 路，试出来的边界）

需求是「每区 2-3 所学校」，实际把东西海朝丰通各区的头部校域名全试了一遍：

- ✅ 可解析 4 所：人大附中（通知公告 + 招生资讯两栏目）、清华附中（招生专栏，title 属性结构规整）、北师大附中（招生专栏）、首师大附中（校园快讯，多为公众号转链价值一般）
- ❌ 动态渲染：101 中学、八中（curl 拿不到 JS 列表）
- ❌ 拒绝/超时：十一学校（403）、北大附中
- ❌ 无独立官网：汇文、五中、陈经纶、八十中、丰台十二中、潞河中学（404）等

结论：**官网路线的天花板就是 4 所**，北京学校官网生态如此（官方信息主场在公众号），「每区 2-3 所」的目标只能靠 wewe-rss 公众号通道补齐。这是需求与现实的差距，如实记录，不做技术上的强行绕过。

### 3.4 知乎 UGC（未上板）

调研中确认知乎话题路由需要登录 cookie（`z_c0` + `d_c0`/`__zse_ck`），cookie 已配在本地 RSSHub 的 `.env`，话题 ID 已拿到（小升初 19778485、小升初政策 28594617）。但看板决策为纯官方信源，知乎源不上板——cookie 也不该进任何云端构建环境。

## 四、版本演进（四版迭代，每次一个明确问题）

| 版本 | 解决的问题 | 形态 |
|---|---|---|
| v1 | 跑通：18 区 + 市级 2 路，Actions 每 6 小时构建 | 20 张卡平铺 90+ 条链接 |
| v2 | 用户反馈「纯链接太混乱」 | 加标签体系（入学政策/招生简章/审核细则）、每卡片要点行、NEW 徽章、旧条目折叠 |
| v3 | 用户反馈「按区分、学校合并」 | 分区卡片：区政策 + 该区学校合并一卡，新增北师大附中/首师大附中 |
| v4 | 设计重做（frontend-design 视角） | 政务台账风格：宋体标题、朱砂红语义色、招生季时间轴 hero、18 行分区台账 |

v4 的设计依据：内容本体是政策文件，视觉语言从题材取——宋体对应红头文件标题、朱砂红只用于语义点（NEW/今天/题线）、纸白底。Hero 是招生季时间轴（市政策→区细则→信息采集→派位→录取），因为这个看板的本质是**强周期工具**：平时静默、4-7 月爆发，时间轴把工作节奏放在第一屏。

## 五、技术细节备忘

- **构建脚本**：`tools/build.py`，纯 Python 标准库（urllib/re/json），Actions 环境零安装直接跑
- **NEW 徽章机制**：构建时与上次 `data.json` 快照 diff（按 id/link 判断），新增条目标红。首跑全标 NEW 属正常现象，第二次起才准
- **数据留痕**：每次构建的 data.json 随仓库提交，政策变化历史可 git log 回溯
- **私有仓 Pages**：GitHub 私有仓库支持 Pages，访问权限随仓库（只有协作者能看板），内部调研不外泄
- **gh 权限**：推送 workflow 文件需要 `gh auth refresh -h github.com -s workflow` 加 workflow scope
- **Actions 警告**：ubuntu-latest 迁移 26 和 Node 20 弃用警告目前无害，`actions/checkout@v4` 等可后续升级

## 六、维护事项

| 事项 | 方法 |
|---|---|
| 某区信源返回空 | 平台改版换 fid：重新抓 `portal_{区}/zszc.html` 源码里 initPaginator 参数，改 build.py 的 DISTRICTS 表 |
| 市教委/教育部解析失效 | 页面改版，重新核对正则（先打印原始 HTML 看真实结构再写） |
| 加学校 | SCHOOLS 表加条目 + 在 PARSERS 里加对应解析器（四种解析器模板：rdfz/qhfz/sdfz/cnuhs） |
| 加公众号信源 | 部署 wewe-rss（微信读书通道），产出走 Actions 拉取或另行入库 |
| 手动触发构建 | Actions 页面按钮，或 `gh workflow run build.yml` |
| 查构建日志 | `gh run watch <run-id>` 或 Actions 页面 |

## 七、与其他工具的关系

看板是信源基建的第四层，不替代前三层：

- **MediaCrawler**（采集）：小红书评论按需采集 + 信源提及分析，产出分析报告
- **RSSHub + NetNewsWire**（订阅）：20 路自动推送，本地 Mac 跑
- **学城文档**（分析与记录）：《信源分析》总纲、01-小升初子文档、信源分析报告（UGC 实测数据）
- **本看板**（展示）：零门槛的团队可见层，Actions 云端自动更新
